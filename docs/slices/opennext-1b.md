## 1. Purpose / risk retired

Plain language (Ratification note 3): with CACHE-10 live, this upgrade does not change what editors or visitors see on
an edit. It retires the risk of running an UNMAINTAINED adapter (open-next 3.1.3, October 2024) in front of every
tenant site: future Next security patches need a maintained adapter, and 4.x carries two routing-bypass fixes (#810,
#1199). It also makes tag revalidation write rows (on 3.1.3 `revalidatePath` wrote nothing — D4), and it closes the
#1250 cold-container cost (every cold STALE enqueued an SQS message that can no longer re-render).

Tie to the vision: one deployment serves many tenants; the serving adapter is the code every public request passes
through. Tenant isolation (B-ISO, `p1 p2 t1 t2`, `h1b h1c`) and "a failure is never cached" (`e1`, `d3`, B-ROUTEERR)
are re-proven on the new adapter's real artefact before any deploy.

How hunk 3 works, under the hood: Next 16.3.8 decides "stale or not" for an ISR read from
`SharedCacheControls.cacheControls`, a per-process `Map` (static class field). Only the process that rendered a page
fills it. A cold Lambda container has an empty map → `calculateRevalidate` falls back to 1 s → every stored entry
older than 1 s is STALE (#1250). The hunk runs inside the cache handler's `get`, before Next reads the map: if the
stored entry carries `revalidate` (4.x writes it on every set), it puts `{ revalidate, expire: undefined }` under the
same route-cache key. With `revalidate: false` Next computes "never stale" and emits `s-maxage=31536000`. The
`require` is a runtime require: OpenNext compiles the cache adapter with `next` external (4.1.9
`build/compileCache.js`), so `cache.cjs` resolves `next/...` from `server-functions/default/node_modules/next` — the
one copy Next's own `incremental-cache/index.js` loads, therefore the same `Map` instance (INFERRED from the layout;
PROVEN by the B-STALE outcome, which is impossible with a second instance).
